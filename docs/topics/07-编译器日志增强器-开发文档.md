# 课题7：编译器日志增强器开发文档

> 文档类型：分层实施指南
> 读者：Topic 7 开发者、评审者和维护者
> 开发基线：仓库当前实现（2026-09-22）
> 先读：[Topic 7 设计文档](07-编译器日志增强器-设计文档.md)

---

## 1. 开发目标

在不改变编译语义、产物内容和 CLI 退出码的前提下，将现有日志基础模块接入 ScratchV 主编译管线，完成终端分级、文件留存、颜色控制、阶段计时和生命周期管理。

开发顺序必须是：

```text
锁定现状 -> 修正基础设施 -> 接入 CLI -> 接入 Driver
-> 按模块接入 -> 回归/性能验证 -> 文档和示例收尾
```

不要从全局批量替换 `print()` 开始。`print()` 中有一部分是用户产物、报表或错误诊断，不属于运行日志。

## 2. 现有代码地图

| 文件 | 当前职责 | 本课题改动 |
|---|---|---|
| `scratchv/utils/logger.py` | logger、formatter、handler、阶段/进度 API | 修正重入、关闭、传播、异常格式化和自动颜色 |
| `scratchv/utils/__init__.py` | 导出部分日志 API | 明确公共导出面 |
| `scratchv/main.py` | CLI 参数、结果展示、退出码 | 新增参数并管理 logger 生命周期 |
| `scratchv/compiler.py` | 编译管线和 `CompilerConfig` | 解耦日志/IR 验证，添加阶段日志 |
| `scratchv/frontend/*` | DSL/ONNX 解析 | 后续添加低频摘要日志 |
| `scratchv/optimizer/*` | IR 优化 | 记录 pass 名、改动数和耗时 |
| `scratchv/backend/*` | 代码生成与后处理 | 记录策略和数量摘要 |
| `tests/test_logger.py` | 基础 API 测试 | 补强输出内容、重入和异常测试 |
| `tests/test_cli.py` 或新测试文件 | CLI 行为 | 增加日志集成与产物不变测试 |

## 3. 开发前基线

### 3.1 环境

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
python3 -m pytest tests/test_logger.py -q
```

记录 Python 版本、基线测试数和失败项。如果基线已失败，先确认是环境问题还是仓库问题，不将无关修复混入本课题。

### 3.2 必须先补的失败测试

1. `shutdown()` 后再调用 `get_logger()` 能重新安装 handler；
2. 连续两次 `init_logger()` 一条日志只输出一次；
3. 初始化为文件 A，再初始化为文件 B，A 可关闭/删除，B 正常写入；
4. 宿主 root logger 存在 handler 时不重复输出；
5. `log.error(..., exc_info=True)` 的文件输出含异常类型和消息；
6. CLI 传 `--log-level DEBUG` 时实际出现阶段日志；
7. 开启日志前后生成的 `.s` 文件字节相同。

## 5. P0：锁定输出契约

### 5.1 区分三类输出

| 类型 | 示例 | 处理 |
|---|---|---|
| 产物 | 汇编、LLVM IR、JSON、HTML | 不转日志 |
| 用户诊断/结果 | caret 错误、最终成功行、命令行表格 | 保留明确渲染器或 CLI 输出 |
| 运行观测 | 阶段开始、耗时、内部决策 | 转为 logger |

评审每一个准备替换的 `print()` 时，都必须先标记它属于哪一类。

### 5.2 基线产物快照

选择一个简单 DSL 用例，保存关闭日志时的：

- 进程退出码；
- stdout/stderr；
- 输出汇编的哈希或字节内容；
- `CompileResult` 的 success/errors/warnings/stats。

后续每一层接入后重复对比。

## 6. P1：稳定日志核心

### 6.1 重构 handler 清理

建议先提取内部函数：

```python
def _close_handlers(logger: logging.Logger) -> None:
    for handler in list(logger.handlers):
        handler.flush()
        handler.close()
        logger.removeHandler(handler)
```

`init_logger()` 和 `shutdown()` 共用该逻辑。不要只调用 `handlers.clear()`。

### 6.2 恢复状态

`shutdown()` 完成后将 `_root_logger = None`、`_initialized = False`，并清理配置快照。测试不应手动修改模块私有状态才能运行。

### 6.3 阻止重复传播

初始化时设置：

```python
root = logging.getLogger("scratchv")
root.propagate = False
```

在测试中给 Python 根 logger 安装一个捕获 handler，验证 ScratchV 消息不向上传播。

### 6.4 保留异常文本

自定义 formatter 在生成主行后，使用 `formatException(record.exc_info)` 和 `formatStack(record.stack_info)` 追加内容。增加精确测试，不要只验证“不抛异常”。

### 6.5 完成标准

- 同一 logger 可初始化—关闭—再初始化；
- 每次初始化后 handler 数符合配置（终端 1，可选文件 1）；
- 文件可在 shutdown 后立即删除/重命名；
- traceback 可见，颜色不泄漏到文件。

## 7. P2：接入 CLI

### 7.1 参数

在 `build_arg_parser()` 中增加：

```python
parser.add_argument("--log-file", help="Write detailed logs to FILE")
parser.add_argument(
    "--color", choices=["auto", "always", "never"], default="auto",
    help="Control colored stderr output",
)
```

`--log-level` 补齐 `CRITICAL`；如需兼容 `WARN`，在参数解析后归一化，不把别名传入内部配置。

### 7.2 初始化位置

在参数验证完成后、`CompilerDriver` 创建前初始化。使用 `try/finally` 确保正常、预期失败和未预期异常路径都关闭 handler。

不建议在 `CompilerDriver.__init__()` 中安装 handler，因为 driver 可能被库调用者创建多次。

### 7.3 CLI 测试层次

1. 参数解析测试：Namespace 字段正确；
2. 函数级 `main([...])` 测试：退出码和 stderr；
3. subprocess 快速冒烟：真实控制台脚本和日志文件；
4. 产物对比：日志开/关的 `.s` 字节相同。

## 8. P3：解耦 CompilerConfig

### 8.1 修复意外耦合

当前 `CompilerDriver.compile()` 使用 `config.use_logger` 判断是否运行 `_verify_ir()`。应将其改为独立字段：

```python
@dataclass
class CompilerConfig:
    verify_ir: bool = False
    use_logger: bool = False
    log_level: str = "INFO"
    log_file: str | None = None
```

`args_to_config()` 将 `--verify-ir` 映射到 `verify_ir`，将日志参数单独映射。

### 8.2 四象限测试

| logging | verify_ir | 期望 |
|---|---|---|
| off | off | 无日志，不运行额外 IR 验证 |
| on | off | 有日志，不运行额外 IR 验证 |
| off | on | 无日志，运行 IR 验证 |
| on | on | 有日志，运行 IR 验证 |

这是本课题最重要的语义回归测试之一。

## 9. P4：接入编译主阶段

### 9.1 接入顺序

1. `CompilerDriver.compile()` 入口和输出摘要；
2. `_parse()`；
3. `_run_optimizations()` 及每个 pass；
4. `_generate_code()`；
5. `_run_asm_passes()`；
6. 输出文件写入。

每一步只在阶段边界添加日志，完成测试后再进入下一步。

### 9.2 推荐代码形式

```python
log = get_logger("compiler")

with log_phase("frontend.dsl", "Parsing DSL input"):
    program = self._parse(input_path, dsl_source)

log.debug(
    "Compiler config: backend=%s optimize=%s reg_alloc=%s",
    self.config.backend,
    self.config.optimize_level,
    self.config.reg_alloc,
)
```

不要在日志中输出 `program` 或 `asm_text` 全文。

### 9.3 PassManager 计时

`PassManager.run()` 当前已计算 `elapsed` 并写入局部 `timings`，但没有将它返回或记录。开发时应二选一：

- 最小改动：在 pass 完成后记录 DEBUG；
- 更完整：将 timings 纳入 `PassResult`/`CompileResult.stats`，日志只渲染该结构数据。

优先选择第二种，因为性能数据不应只存在文本日志中。

## 10. P5：模块级接入

### 10.1 前端

- INFO：解析类型和结束摘要；
- DEBUG：函数数、节点数、输入/输出数；
- WARNING：使用了兼容回退，但编译可继续；
- 用户语法错误由诊断渲染器输出，不在日志里复制源码。

### 10.2 优化器

每个 pass 记录输入规模、改动数和耗时。只在 DEBUG 且明确开启 dump 时输出规则级详情。不使用 INFO 逐条记录优化命中。

### 10.3 后端

记录指令选择模式（linear/DAG）、寄存器分配策略、spill 数、生成汇编字节数和后处理变化数。寄存器映射等高基数数据必须是 DEBUG 且延迟构造。

### 11.5 性能对比

选择固定 DSL 输入，分别测量：无日志、INFO 终端重定向、DEBUG 文件三种模式。先预热，再运行至少 10 次取中位数。不使用单次结果做性能结论。

## 12. 测试矩阵

| 类别 | 用例 | 关键断言 |
|---|---|---|
| 级别 | DEBUG/INFO/WARNING/ERROR/CRITICAL | effective level 和过滤内容 |
| 非法输入 | `INVALID` | `ValueError` 或 argparse 错误 |
| 名称 | `parser`、`scratchv.codegen` | 前缀只有一次 |
| 颜色 | TTY/非 TTY/NO_COLOR/强制 | ANSI 是否存在 |
| 文件 | DEBUG 消息 | 文件有、INFO 终端无 |
| 异常 | `exc_info=True` | traceback 完整 |
| 阶段 | 成功/抛异常 | done/FAILED、耗时、重抛 |
| 进度 | 0/0、5/10、12/10 | 无除零、格式稳定 |
| 重入 | init 两次 | 不重复、旧 handler 关闭 |
| 关闭 | shutdown 两次 | 幂等、可再初始化 |
| CLI | log-level/log-file/color | stderr、文件、退出码 |
| 语义 | logger on/off | 产物和 CompileResult 一致 |

## 13. 常见开发错误

### 13.1 日志输出两次

检查 `scratchv` logger 的 handler 数、`propagate` 和宿主 root logger。不要用在消息中去重的方式掩盖 handler 重复。

### 13.2 测试单独通过，全量失败

通常是模块全局状态没有在 shutdown/fixture 中恢复。为每个测试使用 autouse fixture 做前后清理。

### 13.3 `capsys` 捕获不到内容

handler 在初始化时持有当时的 `sys.stderr`。应在 `capsys`/`redirect_stderr` 生效后初始化 logger，或给 handler 注入 `io.StringIO`进行精确单测。

### 13.4 traceback 消失

自定义 formatter 绕过了 `logging.Formatter.format()` 的异常处理。显式格式化 `record.exc_info`，或在自定义前调用基类逻辑。

### 13.5 开启日志后多了 IR 警告

检查 `CompilerDriver.compile()` 是否仍使用 `use_logger` 作为 `_verify_ir()` 开关。必须改用独立 `verify_ir`。

### 13.6 日志文件含颜色码

文件 handler 必须使用 plain formatter，不得复用开启颜色的 console formatter。

## 14. 代码评审清单

### 14.1 边界

- [ ] 日志不代替 `CompileResult` 中的结构化数据；
- [ ] 汇编、IR、JSON、HTML 产物不含日志；
- [ ] 用户诊断没有被重复打印；
- [ ] 第三方/root logger 未被修改。

### 14.2 正确性

- [ ] 级别映射和过滤正确；
- [ ] 重复初始化不累加 handler；
- [ ] shutdown 幂等且恢复未初始化状态；
- [ ] `log_phase` 不吞异常；
- [ ] traceback 和 stack info 正确保留。

### 14.3 性能与安全

- [ ] DEBUG 消息使用参数化格式；
- [ ] 昂贵 dump 有 `isEnabledFor()` 守卫；
- [ ] INFO 不在高频循环中记录；
- [ ] 没有默认打印模型权重、用户数据或环境变量。

### 14.4 测试

- [ ] 断言真实输出内容，不是只验证无异常；
- [ ] 覆盖 TTY/非 TTY、文件、异常、重入和 CLI；
- [ ] 日志开/关产物对比通过；
- [ ] 相关测试与全量测试都通过。
