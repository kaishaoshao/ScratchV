# 课题7：编译器日志增强器设计文档

> 文档类型：详细设计
> 适用范围：`scratchv/utils/logger.py`、`scratchv/main.py`、`scratchv/compiler.py` 及各编译阶段
> 设计基线：仓库当前实现（2026-09-22）
> 相关文档：[Topic 7 课题说明](07-编译器日志增强器.md) | [Topic 7 开发文档](07-编译器日志增强器-开发文档.md)

---

## 1. 文档目标

本文档定义 ScratchV 统一日志系统的设计边界、数据流、公共 API、配置规则、输出契约、集成方案和验收标准。它同时是：

- 日志模块后续演进的设计依据；
- 各编译阶段接入日志时的约束；
- CLI、单元测试和 CI 判定行为是否兼容的共同契约。

本文档不把目标能力冒充为已实现能力。第 3 节专门审计当前代码，后续章节描述完整目标设计。

## 2. 背景与问题定义

ScratchV 的主编译管线包含 DSL/ONNX 解析、IR 验证、优化、指令选择、寄存器分配、汇编后处理、性能统计和结果输出。这些阶段的运行信息如果由零散 `print()` 输出，会产生以下问题：

1. 无法按严重程度过滤，正常运行信息与警告混在一起；
2. 无法从日志名称定位产生消息的模块和阶段；
3. 终端输出、文件留存和机器可读结果的边界不清；
4. 阶段耗时需手工计时，异常路径容易遗漏；
5. 调试日志可能构造昂贵字符串，影响默认编译性能；
6. 库调用、CLI 和测试之间容易重复配置 handler，造成重复日志或文件句柄泄漏。

因此，Topic 7 的核心不是“给文字上色”，而是建立一套可预测、可过滤、可测试且不污染编译产物的运行观测契约。

## 3. 当前实现审计

### 3.1 已实现能力

`scratchv/utils/logger.py` 已提供：

- `init_logger(level, log_file, use_color)`：配置 `scratchv` 命名空间的根 logger；
- `get_logger(name)`：自动补齐 `scratchv.` 前缀，首次使用时可默认初始化；
- `set_level(level)`：运行时修改终端过滤级别；
- `shutdown()`：刷新、关闭并移除 handler；
- `log_phase()`：记录阶段开始、成功/失败与耗时；
- `log_progress()` 和 `log_step()`：输出进度和调试步骤；
- 终端 ANSI 颜色 formatter 与无颜色文件 formatter；
- 文件 handler 固定保留 `DEBUG` 及以上日志。

`tests/test_logger.py` 已覆盖初始化、名称层级、级别切换、文件输出、进度 API 和阶段成功/失败路径。

### 3.2 集成现状

当前主 CLI 只定义了 `--log-level`，并把它转换为 `CompilerConfig.use_logger` 和 `log_level`，但没有调用 `init_logger()`。编译器主体和前/中/后端也尚未使用 `get_logger()`。

另外，`CompilerDriver.compile()` 当前将 `use_logger` 当作运行 IR 验证的开关，这与日志语义不一致。CLI 也尚未提供课题说明中的 `--log-file`。

因此当前状态应表述为：“日志基础模块已实现，编译管线集成待完成”。

### 3.3 已知技术缺口

| 编号 | 当前行为 | 风险 | 目标行为 |
|---|---|---|---|
| L-01 | CLI 未调用 `init_logger()` | `--log-level` 不产生日志效果 | CLI 解析后、driver 创建前初始化 |
| L-02 | `use_logger` 触发 IR 验证 | 开启日志改变编译语义/开销 | 日志和 `verify_ir` 为独立配置 |
| L-03 | 缺少 `--log-file` | 无法从主 CLI 留存详细日志 | CLI 和 `CompilerConfig` 完整传递路径 |
| L-04 | `shutdown()` 后 `_initialized` 仍为真 | 后续 `get_logger()` 可返回无 handler logger | shutdown 恢复可重新初始化状态 |
| L-05 | 重新初始化直接 `handlers.clear()` | 文件 handler 可未关闭 | 移除前 flush/close |
| L-06 | 未禁止向 Python 根 logger 传播 | 宿主已配置 logging 时可重复输出 | `scratchv` logger 设置 `propagate = False` |
| L-07 | 自定义 formatter 只用 `getMessage()` | `exc_info`/stack 信息可丢失 | 显式追加异常和堆栈文本 |
| L-08 | 颜色默认强制开启 | 重定向文件时出现 ANSI 码 | CLI 按 TTY/`NO_COLOR` 自动决定，允许显式覆盖 |
| L-09 | `_config` 无可见用途 | 状态不透明 | 删除或通过只读配置对象替代 |

## 4. 设计目标与非目标

### 4.1 设计目标

1. 所有编译阶段使用 `scratchv.<subsystem>[.<component>]` 层级命名。
2. 终端和文件可设置不同过滤级别，文件输出不含 ANSI 码。
3. 主 CLI 提供 `--log-level`、`--log-file` 和颜色控制，库使用者仍可直接调用 API。
4. 日志不改变编译成功/失败、优化结果、输出文件和退出码。
5. 为解析、优化、代码生成和后处理提供统一阶段计时。
6. 默认关闭的 DEBUG 日志不构造昂贵中间文本。
7. 初始化、重配置、关闭和测试捕获都可重入、可预测。
8. 不在日志中默认输出模型权重、大量 IR/汇编或用户输入数据。

### 4.2 非目标

- 不在本课题内建设分布式链路追踪、OpenTelemetry 或远程日志服务；
- 不用日志取代 `CompileResult.errors/warnings/diagnostics/stats`；
- 不用日志取代 `--dump-ir`、benchmark JSON 或 HTML 报告；
- 不保证日志文本是稳定的机器 API，机器消费者应使用结构化结果；
- 不为第三方依赖的 logger 统一改级别或格式。

## 5. 设计原则

### 5.1 日志是旁路，不是业务状态

编译结果必须通过 `CompileResult` 传递。禁止通过解析日志来判定编译是否成功、优化改动数或指令数。

### 5.2 库不擅自控制宿主日志

ScratchV CLI 拥有初始化权；被其他 Python 程序当库调用时，不应修改 Python 全局根 logger。所有 handler 只挂在 `logging.getLogger("scratchv")` 上。

### 5.3 延迟格式化

使用：

```python
log.debug("Selected %d machine instructions", len(instructions))
```

不使用：

```python
log.debug(f"Selected instructions: {expensive_dump(instructions)}")
```

必须输出昂贵 dump 时，先检查 `log.isEnabledFor(logging.DEBUG)`。

### 5.4 稳定字段优先

消息使用稳定的阶段名、计数和路径，避免直接输出不可控对象的 `repr()`。路径以用户提供或项目相对形式显示，不额外扫描环境。

## 6. 总体架构

```text
CLI arguments
    |
    v
LoggerConfig ---------> configure_logging()/init_logger()
                            |
                            +--> scratchv root logger (propagate=False)
                            |       +--> console handler -> Color/Plain formatter
                            |       +--> file handler    -> Plain formatter
                            |
CompilerDriver              v
    +--> frontend       get_logger("frontend.dsl")
    +--> verifier       get_logger("analysis.ir_verifier")
    +--> optimizer      get_logger("optimizer")
    +--> backend        get_logger("backend.codegen")
    +--> post passes    get_logger("backend.post")
    +--> reporting      get_logger("report")
```

### 6.1 组件职责

| 组件 | 职责 | 不负责 |
|---|---|---|
| CLI | 解析日志参数、决定颜色策略、初始化一次 | 在模块内重复添加 handler |
| logger 基础设施 | 命名、过滤、格式化、句柄生命周期 | 决定业务成功与否 |
| CompilerDriver | 在阶段边界记录开始/结束/摘要 | 打印每条 IR 指令 |
| 子模块 | 记录本模块可操作的调试事件 | 重新配置全局日志 |
| CompileResult | 保存稳定、可编程的警告/统计/诊断 | 保存每条调试日志 |

## 7. 配置模型

建议引入不可变配置对象，同时保留现有函数式 API 作为兼容层：

```python
@dataclass(frozen=True)
class LoggerConfig:
    console_level: str = "INFO"
    file_path: str | None = None
    file_level: str = "DEBUG"
    color: bool | None = None       # None = auto
    include_timestamp: bool = True
```

约束：

- 级别允许 `DEBUG/INFO/WARNING/ERROR/CRITICAL`，输入大小写不敏感；
- `WARN` 可作为 CLI 兼容别名，内部归一为 `WARNING`；
- `file_path=None` 时不创建文件 handler；
- `color=None` 时只在 `stderr.isatty()` 且未设置 `NO_COLOR` 时启用；
- 日志文件的父目录是否自动创建需有唯一策略。本设计选择“不自动创建”，路径无效时在 CLI 启动阶段清晰失败。

## 8. Logger 命名契约

| 领域 | 名称示例 |
|---|---|
| CLI | `scratchv.cli` |
| DSL 前端 | `scratchv.frontend.dsl` |
| ONNX 前端 | `scratchv.frontend.onnx` |
| IR 验证 | `scratchv.analysis.ir_verifier` |
| 优化管线 | `scratchv.optimizer` |
| 单个 pass | `scratchv.optimizer.constant_folding` |
| 指令选择 | `scratchv.backend.isel` |
| 寄存器分配 | `scratchv.backend.regalloc` |
| 汇编后处理 | `scratchv.backend.post` |
| 报告 | `scratchv.report` |

`get_logger("backend.isel")` 与 `get_logger("scratchv.backend.isel")` 必须返回同名 logger。禁止创建与模块无关的笼统名称，如 `scratchv.misc` 或 `scratchv.test2`。

## 9. 日志级别契约

| 级别 | 语义 | 示例 |
|---|---|---|
| DEBUG | 对开发者有用的内部决策与数量 | pass 改动数、选择的寄存器策略 |
| INFO | 用户可理解的正常阶段和结果摘要 | `Parsing DSL... done (0.012s)` |
| WARNING | 编译可继续，但结果可退化或存在兼容处理 | 不支持的属性使用默认值 |
| ERROR | 当前阶段失败或最终编译失败 | 代码生成抛出异常 |
| CRITICAL | 进程级不可恢复错误 | 基础环境严重损坏；应极少使用 |

同一问题不应在子模块、driver 和 CLI 连续记录三次。规则是：能处理就在处理层记录；不能处理就向上抛出，由最终转换为失败结果的层记录一次。

## 10. 输出格式

### 10.1 终端

```text
14:32:08 INFO     [scratchv.frontend.dsl] Parsing DSL input...
14:32:08 INFO     [scratchv.frontend.dsl] Parsing DSL input... done (0.014s)
14:32:08 DEBUG    [scratchv.optimizer] constant-folding: 3 change(s)
```

终端时间精度为秒，耗时使用单调时钟 `perf_counter()` 且保留 3 位小数。颜色只是展示增强，去掉 ANSI 后文本仍完整。

### 10.2 文件

```text
2026-09-21 14:32:08 INFO     [scratchv.frontend.dsl] Parsing DSL input...
```

文件记录包含日期，不包含 ANSI 码。默认模式为覆盖写入，如果未来增加 append/rotation，必须通过新配置项明确表达，不可静默改变。

### 10.3 异常信息

formatter 必须保留 `record.exc_info` 和 `record.stack_info`。INFO 和 WARNING 默认不输出堆栈；捕获未预期内部错误时，DEBUG 日志文件应可查看完整 traceback。

## 11. 公共 API 设计

### 11.1 初始化

```python
def init_logger(
    level: str = "INFO",
    log_file: str | None = None,
    use_color: bool | None = None,
) -> None: ...
```

保留现有签名以兼容旧调用。重复调用视为“替换配置”：先安全关闭旧 handler，再安装新 handler，不得重复输出。

### 11.2 获取 logger

```python
log = get_logger(__name__)
```

当 `__name__` 已以 `scratchv` 开头时不重复加前缀。新模块推荐在模块顶层获取 logger，但不在 import 阶段配置 handler。

### 11.3 阶段上下文

```python
with log_phase("backend.codegen", "Generating RISC-V assembly"):
    asm_text = self._generate_code(program)
```

成功时记录 INFO；失败时记录 ERROR 并原样重新抛出，不吞异常，不改写异常类型。

### 11.4 进度

`log_progress(name, current, total, description)` 适用于总数已知的长任务。当 `total <= 0` 时显示 `0.0%`；实现应将显示百分比限制在 0–100，但保留原始 `current/total` 便于发现调用错误。高频循环必须由调用方节流，不允许每条指令输出 INFO。

## 12. CLI 设计

```text
--log-level {DEBUG,INFO,WARNING,ERROR,CRITICAL}
--log-file PATH
--color {auto,always,never}
```

策略：

1. 未指定任何日志参数时，保持现有 CLI 简洁输出；
2. 指定 `--log-file` 但未指定 `--log-level` 时，终端为 INFO，文件为 DEBUG；
3. 日志一律写 `stderr`，不向汇编或 JSON 产物的 `stdout` 混入文本；
4. 日志初始化失败属于 CLI 配置错误，返回非零退出码，且不开始编译；
5. `CompilerConfig` 保存业务所需的日志开关/级别，但 handler 生命周期由 CLI 入口管理。

## 13. 编译管线集成

### 13.1 推荐阶段事件

| 阶段 | INFO | DEBUG |
|---|---|---|
| Parse | 输入类型、开始/耗时 | 函数/基本块/节点数，不打印完整模型 |
| IR verify | issue 数摘要 | 规则级别计数 |
| Optimize | pass 数、总耗时 | 每个 pass 改动数与耗时 |
| Codegen | 后端、寄存器分配策略、耗时 | 机器指令数、spill 数 |
| Post passes | 启用的 pass 摘要 | 各 pass 前后指令数 |
| Emit | 输出路径、字节数 | 写入耗时 |

### 13.2 失败路径

`log_phase` 记录阶段失败，`CompilerDriver` 继续按现有契约转换为 `CompileResult`。DSL 用户输入错误属于预期诊断，不应在 ERROR 日志中重复打印完整 caret 报告；CLI 仍由 `render_error()` 输出诊断。

### 13.3 与 `CompileResult` 的边界

- 用户可操作警告：放入 `warnings`，可同时记录 WARNING；
- 性能数据：放入 `stats`，日志只显示摘要；
- 致命错误：放入 `errors/diagnostics`，日志记录阶段和异常类型；
- 编译产物：只写目标文件/结果字段，不通过日志输出完整内容。

## 14. 资源与生命周期

### 14.1 状态机

```text
UNINITIALIZED --init--> ACTIVE --init(new config)--> ACTIVE
      ^                    |
      +------shutdown------+
```

- `get_logger()` 在 UNINITIALIZED 状态可按默认配置进入 ACTIVE；
- `shutdown()` 必须 flush、close、remove 所有 handler，并将状态恢复为 UNINITIALIZED；
- 重新 `init` 不累加 handler，不泄漏文件句柄；
- CLI 在 `finally` 中关闭日志，库调用者也可显式关闭。

### 14.2 并发

Python logging handler 自身提供基本线程安全。本版不支持编译过程中并发重配置 logger；初始化和关闭只能在任务边界执行。多进程写同一日志文件不在当前保证范围内。

## 15. 性能、安全与隐私

### 15.1 性能要求

- INFO 级别下，禁用 DEBUG 日志不得构造 IR/汇编 dump；
- 默认日志对小型 DSL 编译的耗时增量目标不超过 5%，以多次中位数测量；
- 高频事件使用计数摘要，不在每个节点上输出 INFO；
- 文件 handler 的 I/O 开销由用户显式启用承担。

### 15.2 安全约束

- 日志中的文件名、节点名和异常消息必须作为纯文本，不反向执行；
- 终端输出用户可控文本时，应考虑移除非预期控制字符；
- 默认不记录模型张量内容、环境变量、用户凭据或完整绝对路径清单；
- 日志文件路径只来自 CLI/API 显式输入，不使用未经校验的命令替换。

## 16. 测试设计

### 16.1 单元测试

1. 五个标准级别及非法级别；
2. 名称自动前缀、已有前缀和层级继承；
3. 终端有色/无色输出，文件永远无 ANSI；
4. INFO 终端 + DEBUG 文件的双级别过滤；
5. `set_level()` 不修改文件 DEBUG 级别；
6. `log_phase()` 成功、失败、异常不被吞掉；
7. `exc_info=True` 真正包含 traceback；
8. 连续初始化无重复消息；
9. shutdown 后可再次自动/显式初始化；
10. `propagate=False` 避免宿主 root logger 重复输出。

### 16.2 CLI 集成测试

- `scratchv example.dsl --log-level DEBUG`：`stderr` 含阶段日志，输出汇编不含日志；
- `--log-file build.log`：创建无 ANSI 文件，含 DEBUG 详情；
- 无日志参数：保持原有简洁输出和退出码；
- 语法错误：只出现一份用户诊断；
- 无效日志目录：编译未执行，返回明确错误。

### 16.3 回归测试

在开启和关闭日志时分别编译同一输入，必须满足：

```text
success_on == success_off
output_text_on == output_text_off
errors_on == errors_off
process_exit_code_on == process_exit_code_off
```

时间字段不做完整快照比较，而是验证格式和必需子串。

## 17. 兼容性与迁移

- 保留 `init_logger/get_logger/set_level/shutdown/log_phase/log_progress/log_step` 现有名称；
- `use_color: bool` 旧调用保持有效，新的 `None` 表示自动；
- 现有 `print()` 不能批量无差别替换。用户产物、CLI 表格和诊断继续使用明确输出接口；
- 新增 `verify_ir` 独立字段后，`use_logger` 不再影响 IR 验证。这是修正意外耦合，需专门回归测试；
- 日志文本是面向人的界面，不承诺字节级稳定，但级别、logger 名称和输出流属于兼容契约。

## 18. 验收标准

完成状态必须同时满足：

- [ ] 主 CLI 真正支持 `--log-level` 和 `--log-file`；
- [ ] 至少解析、优化、代码生成、后处理、写文件五个阶段接入日志；
- [ ] 日志开关不再触发 IR 验证或其他业务行为；
- [ ] 终端与文件分级过滤符合契约；
- [ ] 重复初始化和 shutdown 后重启无句柄泄漏、无重复输出；
- [ ] 异常堆栈可在 DEBUG 文件中保留；
- [ ] 无 TTY 或禁色模式不出现 ANSI 码；
- [ ] Topic 7 单元测试、CLI 集成测试和项目 L2 验证通过；
- [ ] 开启/关闭日志的编译产物字节一致。

## 19. 风险与权衡

| 风险 | 后果 | 缓解方案 |
|---|---|---|
| 批量替换 `print()` | 改变 CLI 契约或污染产物 | 按模块小步接入，每次加输出流测试 |
| 过多 INFO | 正常编译噪音大 | 阶段级 INFO，决策级 DEBUG |
| 文件永远 DEBUG | 日志过大 | 后续可增加独立 file level 和 rotation，默认保持课题契约 |
| 时间快照不稳定 | 测试偶发失败 | 匹配模式和关键字段，不比较完整行 |
| 模块自动初始化 | 库调用者难以控制 | 保留兼容自动初始化，文档推荐入口显式初始化 |
